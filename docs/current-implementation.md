# TableSyncの現状仕様と構成

2026-10-30。既存READMEのプロトタイプの範囲を引き継ぎ、実装から確認した設計を記録する。

## 要件と対象外
- 運営者が参加者を登録・削除し、条件に応じたグループと店舗候補を作り、案内文・JSON/CSVを持ち出せる。
- 認証・決済・本人確認・店舗予約・実在庫・外部AIによる推論は未実装。`verified`は生成時の固定値で、本人確認の証明ではない。
- マッチングは固定ルールによる候補作成であり、相性や食事条件・予約成立を保証する仕様ではない。

## 構成と処理
| 役割 | 実装の正本 |
| --- | --- |
| 入力、一覧、開催条件、出力ボタン | [index.html](../index.html) |
| 条件、候補データ、状態、計算、描画、保存、出力 | [app.js](../app.js) |
| 表示 | [styles.css](../styles.css) |

- `profile`は入力項目と生成ID/時刻をまとめ、参加者一覧に加えて保存する。参加者の追加・削除後、グループは生成ボタンで作り直す。
- `pairScore`は共通タグ、目的、業種、エリア、雰囲気、予算差、食事条件から0〜100の整数を返す。`groupScore`は全ペアの平均。
- `buildGroups`は目的・エリアで並べた候補を種にし、既存メンバーとの平均点と業種/目的の補正で貪欲に選ぶ。
- グループ作成には最低`max(3, 指定人数-1)`人が必要。残り人数は既存グループへ分散するため、指定人数を超える場合がある。
- `assignRestaurant`は定員で候補を絞り、エリア・平均予算・食事条件・タグ・使用済み候補の点数で選ぶ。候補が無い場合は先頭候補へ戻る。
- `generateMatches`がグループ、候補、平均点、会話のきっかけを組み立てる。候補と案内文の生成に外部APIは使わない。
- `renderMatches`の売上指標は割当人数×入力参加費の計算で、入金・決済の記録ではない。

## データ境界
- 参加者だけを同一ブラウザの`localStorage`キー`tablesync-participants`へ保存する。開催条件とグループはメモリ上にあり、再読込で再生成が必要。
- 未保存・JSON不正・空配列の保存はデモ参加者へ戻る。全削除した状態も再読込するとデモへ戻る。
- 保存済み配列の各要素のスキーマ検証と、保存領域が拒否された場合の復旧処理はない。
- JSONには開催条件・全参加者・グループを含む。CSVはグループに割り当てた参加者と候補を含み、`Blob`で利用者がダウンロードする。
- `csvCell`は引用符を二重化する。任意の表計算ソフトでの数式解釈を防ぐ処理は実装されていない。
- 参加者データを送信するネットワークAPI・サーバー・アカウント同期はない。取得した出力ファイルには参加者の入力情報が含まれる。

## 変更時の検証条件
- 合成した参加者だけで、登録/削除/再読込、壊れたJSON、空配列とデモ復帰を確認する。実参加者のデータを試験資料へ使わない。
- 参加人数が作成条件未満なら0グループ、作成できる場合は各参加者の重複割当がないこと、余り人数の扱いを確認する。
- ペア点・グループ点が0〜100で、同じ入力が同じ割当を作ることを確認する。
- 店舗候補が定員条件を満たす場合と候補が空の場合のfallbackを区別して確認する。
- JSON/CSVの対象範囲、引用符・改行、案内文更新、保存データを含むダウンロードを確認する。
- 現在、リポジトリに自動テストやpackage manifestはない。上記は次の変更で満たす確認条件であり、今回の動作試験結果ではない。
